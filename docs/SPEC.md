# Luna 仕様書

## 1. 文書の位置づけ

本書は、Lunaの外部仕様を定義するドキュメントである。ユーザーや外部システムから見た振る舞い、インターフェース、設定項目、エラー時の挙動を規定する。内部設計や実装方針については [ARCHITECTURE.md](./ARCHITECTURE.md) を参照すること。

## 2. 製品の責務と対象範囲

Lunaは、DiscordとローカルHTTP API、Home Assistantを入力とする単一ユーザー向けの自律ワークスペースエージェントである。1つの配置につき、1つのDiscord Bot、1つのワークスペース、1つのChatGPTの資格情報を持つ。

### 主な責務

- Discordの投稿を会話単位に集約し、エージェントのセッションへ渡す。
- HTTPで受けたイベントを独立した実行または会話セッションへ渡す。
- エージェントが呼び出したツール（メッセージ送信・返信・リアクション、シェル、ファイル、Web検索、画像生成等）を即時に実行する。
- 定期ハートビートおよびスケジュール設定に基づき、自律的にエージェントを実行する。
- `LUNA.md`（人格設定）、`MEMORY.md`（長期記憶）、ワークスペースのskill一覧をロードし、セッションのシステムプロンプトを構築する。
- アイドル終了前の会話ログを日次記憶に保存し、定期cronにより記憶とワークスペースを自律的に整理する。
- 長い作業をバックグラウンドタスクとして作業エージェントへ委任し、会話を止めずに進捗・質問・結果を依頼元へ届ける。
- 会話・イベント実行・タスク・オートメーションの現在の状態と直近の出来事を、閲覧専用のWebダッシュボードで示す。
- Home Assistantの状態の取得と操作、状態変化をきっかけにした実行、Assistの会話エージェントとしての応答を行う（§22）。

### 非対象範囲

マルチテナント運用、Windows環境、ダッシュボード以外のWeb UI（操作を伴う画面を含む）、外部公開用CLI、HTTPヘルスチェックエンドポイント、Discord上からの過去セッション再開は対象外とする。

## 3. 信頼境界とセキュリティ

本システムは、Discordの参加者を非特権ユーザーとして隔離しない。Botと対話可能なすべてのユーザー、他のBot、Webhookは、エージェントを介して実行環境の権限を間接的に行使できる。
ローカルHTTP APIも認証を行わず、呼び出し元に同じ権限を与える。Native起動では既定で `127.0.0.1` にバインドし、Docker Composeではホスト側の `127.0.0.1` にのみ公開する。別ホストのHome AssistantからAssistの会話エージェント（§22.4）として使う場合は `LUNA_HTTP_HOST=0.0.0.0` とし、到達可能なネットワーク内の全員に同じ権限を与える。

ダッシュボード（§21）は閲覧専用で認証を行わない。会話本文、ツールの入力、タスクの指示と報告を表示するため、到達できる者はそれらを読める。既定では `127.0.0.1` にバインドし、`LUNA_DASHBOARD_HOST=0.0.0.0` を指定した場合は到達可能なネットワーク内の全員が閲覧できる。

デスクトップ（§23）を入れた場合、neko のパスワードを知る者は、ルナのログイン済みの Chrome を含むデスクトップを見て操作できる。neko はLANへ待ち受ける。

エージェントの実行環境には以下の権限が与えられる。

- サンドボックス: なし
- ユーザー承認: なし
- ファイルシステム: 実行ユーザーがアクセス可能な全範囲の読み書き
- コマンド実行: ホストネットワークの利用、パスワードなしsudoを含む特権昇格
- Discord操作: Botがアクセス可能なすべてのチャンネル、スレッド、DMへの読み書き・送信
- Home Assistant操作: 設定したトークンのユーザーが行えるすべての操作（§22）

実行前の確認プロンプトや、管理者限定コマンド、コマンドやファイルパスのホワイトリストは設けない。Discordのメンション機能も標準準拠であるため、Botの権限範囲内において `@everyone` や各ロールへの通知が可能である。

## 4. 用語定義

- **会話スコープ (Conversation Scope)**: 単一のGuildチャンネル、Guildスレッド、またはDM。
- **HTTP会話セッション**: 同じ `session_id` を持つHTTPイベントが共有する会話状態。Discordの会話状態とは独立する。
- **会話セッション (Conversation Session)**: スコープごとにメモリ上で保持される状態。メッセージキュー、エージェントのセッション、アイドルタイマーを管理する。
- **`LunaEvent`**: 入力元に依存しない共通イベントエンベロープ。`id`、`type`、`source`、任意の `subject`、タイムスタンプ `occurredAt`、JSON形式の `data` を保持する。
- **`ConversationSession`**: 会話を一意に識別する `key`、`source`、プロバイダ固有の `context` を保持する情報。
- **エージェントのセッション**: 1つの会話、1回のイベント実行、または1件のタスクの試行で使う、モデルとの一連のやりとり。システムプロンプト、ツール、モデル、記録を持つ。
- **実行 (Run)**: エージェントのセッションに入力を渡してから、モデルがツール呼び出しを終えて応答を終えるまでの一連の処理。実行中に届いた入力は同じ実行の次のリクエストに入る。
- **ツール**: エージェントが実行中に呼び出す操作。名前、説明、入力スキーマ、実行処理を持ち、呼び出された時点で実行して結果をエージェントへ返す。
- **常設チャンネル**: `allowed_channel_ids` に登録されたGuildチャンネル、またはLunaが参加している対象チャンネル配下のスレッド。メンションなしで常時メッセージを受け付ける。
- **一時セッション**: 常設でないチャンネルやスレッドにおいて、メンションまたは会話委譲により開始された30分間のセッション。
- **会話委譲**: イベント実行や別の会話から `open_conversation` を用い、指定したスコープのセッションへ背景情報を渡して対話を委ねる機能。
- **セッション記憶保存**: アイドル終了を迎えた会話のエージェント自身が、要約や決定事項を `memory/YYYY-MM-DD.md` に追記する処理。
- **日次整理**: 定期cronによって専用のセッションを起動し、記憶やワークスペース内のファイルを整理してローカルGitコミットを作成する処理。
- **バックグラウンドタスク**: 会話またはイベント実行（依頼元）が `task_create` で作業エージェントへ委任した作業。状態と報告は `LUNA_HOME/tasks/` に永続化される。
- **作業エージェント (Worker)**: バックグラウンドタスクを1件ずつ専用のセッションで実行するLuna。Discordへは投稿できず、`task_report` で依頼元へ報告する。
- **タスク一覧**: 会話・イベントの入力に同梱される、その実行から見えるバックグラウンドタスクの現在状態。

## 5. Discord連携

### 5.1 受付条件

Luna自身の投稿を除き、以下のメッセージ（`messageCreate`）を受け付ける。

- 常設チャンネル内のすべてのメッセージ
- 常設でないチャンネルまたはスレッドで、Luna宛てにメンションされたメッセージ
- 一時セッションが有効なスコープへ届いたすべてのメッセージ
- `allow_dm = true` の環境に届いたすべてのDM

人間、他のBot、Webhook、Discordのシステムメッセージはすべて入力として受け付ける。メッセージの編集やリアクションの追加・削除は新規の実行を開始しない。また、親チャンネルで一時セッション中であっても、その配下に作成されたスレッドにはセッションが自動継承されない（スレッド側でのメンションが必要）。

Guildチャンネル配下のスレッドおよびフォーラム投稿は、受信時点でDiscord.jsのキャッシュにLuna自身のメンバー情報が存在する場合にのみ常設として扱われる。キャッシュに存在しない場合は未参加とみなし、常設としては扱わない（外部APIへの追加問い合わせは行わない）。

### 5.2 スコープ管理

Guildチャンネル、Guildスレッド、DMはそれぞれ独立した会話スコープとして扱われ、スコープごとに固有の会話セッションが割り当てられる。同一スコープ内の参加者は単一のエージェントのセッションを共有する。

### 5.3 集約と順序制御

- 最後に受信したメッセージから `debounce_ms` 待機する。
- スコープ内でユーザーが入力中（typing）の場合、入力が止まって `typing_idle_ms` 経過するまで待機する。
- 待機中に受信したメッセージは、Discordの送信時刻順（同値の場合はメッセージID順）に1つのバッチへまとめる。
- すでに実行中の場合はバッチ化せず、受信順に1件ずつ即座に割り込み入力として渡す。割り込み入力は、実行中のツール呼び出しが終わった後、次のモデルへのリクエストの前に入る。

### 5.4 初回コンテキスト

新規セッション開始時は、最初のメッセージバッチより直前の過去ログを最大 `initial_history_limit` 件取得し、古い順にエージェントへ渡す。これ以降の会話履歴はエージェントのセッション側で保持されるため、Discord APIからの再取得は行わない。Gatewayの切断中に受信できなかったメッセージの補完は行わない。

### 5.5 入力の形式

エージェントへの入力は種類（`kind`）付きのメッセージとして渡す。各メッセージはモデルには `<luna_input kind="...">` で包んだuserメッセージとして見え、本文は検証済みのオブジェクトを `JSON.stringify` したものとする。

| `kind`                                            | 本文                                                | 渡す場面                                                 |
| ------------------------------------------------- | --------------------------------------------------- | -------------------------------------------------------- |
| `discord_message`                                 | `discord.message.created.v1` の `LunaEvent`         | 会話への投稿                                             |
| `delegated_conversation`                          | `discord.conversation.delegated.v1` の `LunaEvent`  | 会話委譲                                                 |
| `task_report`                                     | `luna.task.reported.v1` の `LunaEvent`              | タスクの報告の通知（§20.6）                              |
| `heartbeat` / `schedule` / `memory_maintenance`   | 各 `system.*.fired.v1` の `LunaEvent`               | オートメーション                                         |
| `http_request`                                    | `source: "http"` の `LunaEvent`                     | HTTPイベント                                             |
| `home_assistant_state`                            | `home_assistant.state_changed.v1` の `LunaEvent`    | Home Assistantの状態変化（§22.3）                        |
| `assist_request`                                  | `home_assistant.assist.requested.v1` の `LunaEvent` | Assistへの発話（§22.4）                                  |
| `event`                                           | 上記以外の `LunaEvent`                              | その他のイベント                                         |
| `history`                                         | `LunaEvent[]`                                       | 会話セッションの最初の実行（初回コンテキストがある場合） |
| `task_board`                                      | `TaskSummary[]`（§20.5）                            | 会話とイベント実行の各実行の開始時                       |
| `session_end`                                     | `{ date: string }`（ローカル日付）                  | セッション記憶保存                                       |
| `task_assignment` / `task_message` / `task_check` | §20.3                                               | 作業エージェント                                         |

- HTTPイベントの `data` は `{ payload: 送信されたevent.data, response_mode }` であり、IDと受信時刻はLunaが生成する。
- 添付ファイルはURLやメタデータのみを渡し、ランタイム側でのファイル自動ダウンロードは行わない。

### 5.6 スラッシュコマンド

起動時にグローバルコマンド `/luna` を登録する。通常のメッセージを受け付けるスコープで利用可能である（未登録チャンネルでは一時セッション中のみ）。応答は実行者にのみ表示されるエフェメラルメッセージとする。

- `/luna model [model] [effort]`: セッションで使用するモデル（`provider/model`）と推論強度を変更する。モデルのカタログにある組み合わせのみ受け付け、現在のセッションに即時適用する（セッション終了時に設定は破棄される）。
- `/luna end`: 現在のセッションの終了を要求する。実行中の処理と記憶保存の完了を待ってセッションを閉じる。
- `/luna channel add` / `/luna channel remove`: 実行したチャンネルを常設チャンネルに追加または削除する。Guild内であれば誰でも実行可能であり、`config.toml` を更新して即座に反映する。

## 6. 会話セッションのライフサイクル

セッションのアイドル判定時間は `session_idle_ms`（デフォルト30分）とする。
実行が完了し、未処理キューが空になった時点から計測を開始する。実行中（`wait` ツールでの待機を含む）は計測されない。新たなメッセージを受信した場合はタイマーをリセットし、再び処理完了後に計測を行う。

アイドル期限に達した場合、あるいは安全なシャットダウン時に処理中の実行が完了した場合、セッション記憶保存が実行される。

セッション記憶保存が有効な場合、同じエージェントのセッションへ `session_end` を渡して実行する。エージェントは会話全体を要約し、`memory/YYYY-MM-DD.md`（当日のローカル日付）に追記する。保存処理が完了すると、セッションを閉じる。

## 7. ワークスペース

ワークスペースは `LUNA_HOME/workspace` に配置される。起動のたびに、以下のファイルのうち存在しないものをテンプレートから生成する（既存ファイルは上書きしない）。

- `LUNA.md`: エージェントの人格および対話方針。
- `MEMORY.md`: 長期記憶の起点ファイル。記憶の読み方と、トピック記憶の索引を持つ。
- `HEARTBEAT.md`: ハートビート時に確認するチェックリスト。
- `AGENDA.md`: ルナが続けたいこと・引き受けた約束・気になっていることの一覧。各項目は種類、対象者、次の一手、再開条件、関連を持つ。
- `cron.toml`: スケジュール実行の設定（§13）。週次の見直し `self-review-weekly`（日曜15:00）を持つ。
- `.agents/skills/cron/SKILL.md`: スケジュールタスクの登録・管理手順。
- `.agents/skills/heartbeat/SKILL.md`: ハートビート運用の手順。

ワークスペースのディレクトリが存在しない初回起動時だけ、次のファイルも生成する。ルナが整理で移動・改名・アーカイブし得るため、以降の起動では作り直さない。

- `memory/topics/know-how.md`: 入力の読み方、調べ方、制作と作業の進め方、時刻の扱いのコツ。
- `users/README.md`: 利用者ごとのファイル `users/<Discord ユーザーID>.md` の書き方。
- `.agents/skills/self-review/`: 週次の見直しの手順とスクリプト。作業エージェントが直近7日の会話から苛立ちや喜ばれた場面を拾い、`LUNA.md`・`MEMORY.md` の変更案を作り、`luna-chat replay`（§8.2）で現行と盲検で比べる。悪くなった場面がなく、狙った場面がよくなった時だけ、元のファイルを作業ディレクトリへ控えてから反映する。
- `.agents/skills/x-status-fetch/`: XのURLや投稿IDから投稿をFxEmbedのAPI（`api.fxtwitter.com`）で取得する手順とスクリプト。

`intents.toml`（話題をきっかけにする予定、§13.2）と `home-assistant.toml`（状態変化をきっかけにする実行、§22.3）は任意で、初回には生成しない。同梱のスクリプトはPython 3で実行する。

エージェントのセッションを開くたびに、固定の開発者指示、`.agents/skills/` 配下のskill一覧（Agent Skillsの `SKILL.md` の名前・説明・パス）、`LUNA.md` と `MEMORY.md` の全文をこの順に連結してシステムプロンプトとする。作業エージェント（§20）は `LUNA.md` と `MEMORY.md` を読み込まず、タスクに必要な時に自分で読む。skillの本文は事前に読み込まず、エージェントが必要な時に `SKILL.md` を読む。日次記憶 `memory/YYYY-MM-DD.md` とトピック記憶 `memory/topics/*.md` も事前に読み込まず、エージェントが必要な時に検索して該当部分だけを読む。

固定の開発者指示は、実行の種類ごとに次を含む。

| 種類             | 開発者指示                                                                                                                   |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 会話             | 共通の指示、会話の指針、記憶保存（`session_end`）の手順、Discordの使い方、依頼元としてのタスクの使い方、Assistへの返答の仕方 |
| イベント実行     | 共通の指示、会話の指針、HTTP・ハートビート・日次整理の手順、Discordの使い方、依頼元としてのタスクの使い方                    |
| 作業エージェント | 作業エージェントの指示                                                                                                       |

Home Assistantの接続を設定した場合（§22）は、どの種類にもHome Assistantのツールの使い方を加え、会話とイベント実行には `home-assistant.toml` と状態変化の入力の扱い方も加える。

会話の指針は、禁止の一覧ではなく振る舞い方として書く。依頼は実行して結果で返す、依頼の範囲や条件を自分で変えない、確かめられることは確かめてから話す、相手が今ほしいことだけを書く、呼ばれたら必ず応える、指摘はその場で直して自由を保つ、の各項目からなる。唯一の禁止として、体調・怪我・気分の落ち込みの話では、どれほど深刻に見えても緊急・医療の案内（119・#7119、受診の勧め、相談窓口、安全確認、症状の確認項目）をせず、友人として会話で応じる。

エージェントがワークスペースの指示や記憶（`LUNA.md`・`MEMORY.md`・`HEARTBEAT.md`・`AGENDA.md`・`users/`・`prompts/`・`cron.toml` の prompt・`intents.toml`・skill）を書き換える時は、次のように書く。

- 原則とすべきことを、強調語を使わない普通の言葉で書く。同じ原因から来た複数の行は、それらを説明する1つの原則に置き換え、吸収した行を消す。
- 同じ誤りが繰り返されたら、規則を足さずに、原則へ「Not: … Instead: …」の対比例を2つまで添える。
- 人が好んだことや頼んだことは、ルナがしたいこととして日付や経緯を付けずに書く。
- 「Xは動かない」「Yはできない」のようなツールや能力についての否定的な主張は残さない。原因が直った後も拒否として残るため。
- 禁止の一覧は、すべきことに書き直すか、役に立たなければ削除する。

ツールの引数に `.agents/skills/<名前>/SKILL.md` のパスが含まれる `read` と `exec_command` の呼び出しを、そのskillの使用として `LUNA_HOME/state/skill-usage.json`（skill名ごとの最終使用時刻と回数）に記録する。

## 8. エージェントの実行基盤

エージェントは、Lunaのプロセス内でpi（`@earendil-works/pi-agent-core` と `@earendil-works/pi-ai`）を使って実行する。モデルの提供元は `openai-codex`（ChatGPTのサブスクリプションをOAuthで使う）とする。

- 会話・イベント実行・作業エージェントは、それぞれ `[models]`（§14.1）で指定したモデルと推論強度を使う。会話は `/luna model` でセッションごとに変更できる。
- モデルへの各リクエストには `request_timeout_ms` を適用する。
- 成功した応答に提供元の診断情報（WebSocketが使えずSSEで送り直した等）が付いていたら、warnログ `agent.pi.provider_diagnostic` に種類・詳細・エラーメッセージを記録する。
- 一時的な失敗（HTTP 5xx、接続の失敗・切断、タイムアウト）は、15秒・60秒・180秒待って最大3回、同じセッションの続きから再実行する。待機中に届いた割り込み入力は、再実行の前に入る。使用枠の上限到達（HTTP 429 の `usage_limit_reached`）、認証の失敗、それ以外の失敗は再実行しない。
- 直近のリクエストの入力トークン数がモデルの文脈長から予約分（16384トークン）を引いた値を超えたら、`[models.compaction]` のモデルで古い部分を要約し、以後のリクエストでは「システムプロンプト、要約、直近の約20000トークン分」を送る。
- セッションの記録は `LUNA_HOME/sessions/<YYYY-MM-DD>/<セッションID>.jsonl` に追記する（§15）。

### 8.1 認証と使用枠

- ChatGPTの資格情報は `LUNA_HOME/auth/credentials.json`（ディレクトリは0700、ファイルは0600）に保存する。`luna-chat login` を実行すると、デバイスコード方式でログインして保存する。表示されたコードを任意の端末のブラウザで入力する。
- アクセストークンは期限の5分前からリクエストの直前に更新する。更新に失敗した実行は再試行せずに失敗とし、エラーログを記録する。次に実行が成功するまで、ダッシュボードに再ログインが必要であることを示す。
- 使用枠は起動時と以後10分ごとに取得し、`LUNA_HOME/state/usage.json` に書き出してダッシュボードに表示する。書き出す内容は `UsageSnapshot`（取得時刻、プラン、limitごとのprimary・secondaryウィンドウの使用率・長さ・リセット時刻）とする。

### 8.2 再生 (`luna-chat replay`)

`luna-chat replay --scenes <file> --out <ディレクトリ> <名前>=<ディレクトリ>...` は、記録した入力を会話の指示で再生し、指示の違いによる振る舞いを比べる。ルナが自分の人格や記憶の変更案を確かめるのにも使う。

- 場面ファイルはJSONの配列で、各場面は `{ id, note?, inputs: [{ kind, text }] }`。`inputs` は会話の記録（§15）の `luna_input` と同じ形で、1回の実行に渡す入力の列とする。
- 位置引数の指示の組（`<名前>=<ディレクトリ>`）ごとに、そのディレクトリの `LUNA.md` と `MEMORY.md` を、会話と同じ開発者指示と現在のワークスペースのskill一覧に連結してシステムプロンプトとする。指示の組は1つ以上、名前は重複不可。
- モデルは `[models.conversation]`、リクエストのタイムアウトは `request_timeout_ms` を使う。資格情報は通常の実行と同じものを使う。
- ツールは会話と同じものを渡すが、外へ作用させない。Discordへの投稿・リアクション、会話の委任、タスクの作成・指示・取消、Assistへの返答は呼び出しを記録して成功を返す。Home Assistantのツール（§22.1）は渡さない。`exec_command`・`write_stdin`・`edit`・`write`・`image_gen` は実行せずに記録して成功を返す。`read`・`view_image`・`web_run` は実際に実行する。Discordの履歴の読み取りは空を返す。
- 1つの場面でツール呼び出しが12回に達したら、その場面の実行を打ち切る。
- 出力先に、全結果の `results.json`（場面・指示の組・終了状態・ツール呼び出しの列）、場面ごとに候補の並びを無作為に入れ替えて A, B… と名付けた `blind.json`、その対応の `blind-key.json` を書く。再生の会話記録は残さない。

## 10. 実行の制御

最終応答の本文はどこにも送らず、記録にだけ残す。Discordへの発言はすべてツールで行い、返信しないこともエージェントの判断として認める。

### 10.1 HTTP応答 (`http_respond`)

HTTPの完了待ち入力には `http_respond` を利用できる。入力は `{ request_id: string, status: number, body_json: string }` とし、`body_json` はJSONとしてパースできる文字列とする。HTTPレスポンスは実行の完了後に確定する。

### 10.2 待機 (`wait`)

`{ duration_seconds: number }` を指定して指定秒数待機し、同じ実行の中で続ける。`duration_seconds` は1以上 `2147483` 以下の整数とする。待機中に届いた入力は待機の後に入る。実行の中断（バックグラウンドタスクの取消・停止）で打ち切られ、ツールの失敗として扱われる。

## 11. ハートビート

バックグラウンドで自律動作する、ルナの確認と自由時間である。前回のハートビート完了後、`min_interval_ms` から `max_interval_ms` の間でランダムに決定された間隔を経て次回が実行される。

実行時は `HEARTBEAT.md` と `AGENDA.md` を読み込み、`system.heartbeat.fired.v1`（`data` は `{ checklist, agenda }`）として新しいセッションでワンショット実行する。どちらかが読めない場合はその回を実行せずエラーログを記録し、次回を予約する。完了後はセッションを閉じる。

エージェントはチェックリストを処理した後の時間を、何かを前へ進めるために使う。再開条件を満たした、または進めたいアジェンダの項目の次の一手を進める、気になることを調べる、`times-luna🌙` へ話したいことを投稿する、のいずれかを選ぶ。投稿の前に、自分から投稿した最近の発言への反応（リアクションと返信）をチャンネルの履歴で見て、反応のあった方向を選ぶ。数分以上かかる一手はバックグラウンドタスクへ委任し、実行中のタスクがあれば重複させずに続ける。項目の次の一手と再開条件を更新する。アジェンダが空に近い場合は、中核記憶の約束、最近の日次記憶の未完了事項、自分の関心から項目を補う。することが本当にない回は、作業を作らずに終える。

アジェンダはハートビートのほか、セッション記憶保存（約束・やりたいフォローアップ・回答待ちの質問を追加）と日次整理（終わった項目の削除、古い次の一手の修正、新しい関心の追加）で更新される。

## 12. 記憶とワークスペースの日次整理

`[memory].enabled = true` の場合、指定されたcronスケジュール（`maintenance_cron`）に基づいて日次整理タスクが実行される。

- 専用のセッションが起動し、前回の整理以降の日次記憶（少なくとも前日と当日）、`MEMORY.md`、`memory/topics/`、ワークスペース全体を確認する。
- `MEMORY.md` は全セッションが読み込む中核記憶として16000文字以内に保ち、詳細な経緯・手順・制作物の知識は `memory/topics/<topic>.md` へ移して `MEMORY.md` には1行の参照を残す。`MEMORY.md` に入れるのは、続く好みや関係、約束、別の日にも出てきたことのように、セッションをまたいで当てはまるものに限る。
- 人についての事実を `MEMORY.md` や `users/` へ移す前に、`LUNA_HOME/sessions/` の会話記録で実際の発言と照らし合わせ、合わない日次記憶を直す。ハートビート・スケジュール実行・作業エージェントの出力や過去のメモだけを根拠にしない。
- ワークスペースで大きいディレクトリを確かめ、試行の環境、途中のコピー、やり直しの残り、古いバックアップ、作り直せるものをゴミ箱（§15.1）へ移す。成果物、人から預かった原本、認証情報、続いている作業に要るものは残す。
- `LUNA_HOME/state/skill-usage.json` で30日使われていないskillは、`cron.toml`・`HEARTBEAT.md`・`prompts/`・他のskillから参照されていなければ `.agents/skills-archive/<名前>/` へ移す。必要になれば戻す。12000文字ほどを超えた `SKILL.md` は、詳細を `references/` へ移して概要にする。
- 古い情報の整理、不要ファイルの削除などを自律的に行う。
- Gitが利用可能な環境であれば、整理完了後に `Luna <luna@localhost>` 名義でローカルコミットを作成する。リモートへのpushは行わない。

## 13. スケジュール実行

`LUNA_HOME/workspace/cron.toml` に記述されたタスクを定期的に実行する。設定ファイルは自動監視され、再起動なしで変更が反映される。

```toml
[[jobs]]
id = "daily-summary"
enabled = true
kind = "recurring"
cron = "0 21 * * *"
prompt = "今日の会話を確認して、必要ならDiscordへ要約を送る"

[[jobs]]
id = "one-time-reminder"
enabled = true
kind = "one_shot"
at = "2026-08-01T09:00:00+09:00"
prompt = "指定されたリマインドを実行する"
```

各ジョブは発火時刻に `system.schedule.fired.v1` イベント（`data` は `{ jobId, prompt, kind }`）として新しいセッションで実行される。ワンショットジョブ（`kind = "one_shot"`）は、実行開始直後に設定ファイルから自動的に削除される。

定期ジョブ（`kind = "recurring"`）は、同じジョブの前回の実行（後述のcheckを含む）が完了していなくても、次の発火時刻に前回を待たず独立して実行される。重複実行は抑止しない。発火後に `cron.toml` が変更・削除されても、発火済みの実行は発火時点の定義で最後まで続く。

### 13.1 事前判定コマンド (`check`)

定期ジョブには任意の `check`（空白のみでない文字列）を指定でき、発火のたびにエージェントを起動するかをシェルコマンドで事前判定できる。ワンショットジョブに `check` を指定した `cron.toml` は不正として扱う。

```toml
[[jobs]]
id = "release-watch"
enabled = true
kind = "recurring"
cron = "*/30 * * * *"
check = "./scripts/check-release.sh"
prompt = "data.check_output にある新しいリリースを要約し、Discordチャンネル(ID: 1234567890)へ報告する"
```

- 発火時、エージェントを起動する前に、ワークスペースディレクトリをカレントディレクトリとして `/bin/sh -c <check>` を実行する。
- 環境変数はLunaプロセスのものから `DISCORD_BOT_TOKEN` を除いて渡す。標準入力は閉じた状態とし、読み取りは即座にEOFとなる。
- タイムアウトは120秒固定とする。超過した場合はcheckのプロセスグループへSIGTERMを送り、5秒後もなお終了していなければSIGKILLを送って、失敗として扱う。

| checkの結果                                         | 挙動                                                                                                                                                                                                                                        |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 終了コード0、前後の空白を除いた標準出力が空でない   | `system.schedule.fired.v1` を実行する。`data` に前後の空白を除いた標準出力を `check_output` として加える。32000文字を超える場合は先頭32000文字に切り詰め、`check_output_truncated: true` を加える（超えなければこのフィールドは付けない）。 |
| 終了コード0、前後の空白を除いた標準出力が空         | エージェントを起動しない。infoログ `automation.schedule.check_skipped` を記録する。                                                                                                                                                         |
| 非0終了、シグナルによる終了、タイムアウト、起動失敗 | エージェントを起動しない。errorログ `automation.schedule.check_failed` に終了コード・シグナル・タイムアウト有無・エラーを記録する。標準エラー出力の末尾2000文字は `LOG_LEVEL=debug` または `trace` のときのみ出力する。                     |

`check` の追加・変更・削除はジョブ定義の変更として扱い、ジョブを再登録する。`occurredAt` はcheckの完了時刻ではなく発火時刻とする。

### 13.2 話題をきっかけにする予定 (`intents.toml`)

「誰かが旅行の話をしたら感想を聞く」のように、時刻ではなく話題をきっかけにする予定を、ワークスペースの `intents.toml` に書く。エージェントが自分で編集する。ファイルがなければ予定はない。

```toml
[[intents]]
id = "ask-trip"
keywords = ["旅行", "北海道"]
action = "旅行の感想を聞く"
expires_at = "2026-12-01T00:00:00+09:00"
cooldown_hours = 24   # 省略時24
max_fires = 3         # 省略時3
```

- `id` は一意、`keywords` は1つ以上、`action` は空でない文字列、`expires_at` はオフセット付きISO 8601とする。不正なファイルはエラーログを記録し、予定がないものとして扱う。
- 会話セッションが受け付けた人（author が human）のDiscordメッセージの本文に、キーワードのいずれかがNFKC正規化と小文字化の上で含まれ、期限前で、発火回数が `max_fires` 未満で、前回の発火から `cooldown_hours` 以上経っていれば発火する。
- 発火すると、その会話へ `intent` 入力（`{ id, action, keyword, messageId, firesRemaining }`）を、該当メッセージの直後（実行の開始時はタスク一覧の前、実行中はsteerで）に渡す。発火回数と時刻は `LUNA_HOME/state/intents-state.json` に記録する。

### 14.1 `config.toml`

`LUNA_HOME/config.toml` でシステム全体の動作パラメータを設定する。`[memory]` セクションのみが必須で、他は省略可能である。

```toml
[discord]
allowed_channel_ids = []
allow_dm = true
debounce_ms = 5000
typing_idle_ms = 10000
session_idle_ms = 1800000
initial_history_limit = 20

[heartbeat]
enabled = true
min_interval_ms = 900000
max_interval_ms = 2700000

[memory]
enabled = true
maintenance_cron = "0 4 * * *"

[agent]
request_timeout_ms = 300000
transcript_retention_ms = 604800000
transcript_cleanup_interval_ms = 86400000

[models.conversation]
model = "openai-codex/gpt-6.1-sol"
thinking = "medium"

[models.event]
model = "openai-codex/gpt-6.1-sol"
thinking = "medium"

[models.worker]
model = "openai-codex/gpt-6.1-sol"
thinking = "medium"

[models.compaction]
model = "openai-codex/gpt-6.1-terra"
thinking = "low"

[tasks]
max_concurrent = 2
```

- `[models.*]` の `model` は `provider/model` の形とし、`thinking` は `off`・`minimal`・`low`・`medium`・`high`・`xhigh` のいずれかとする。起動時に、提供元のモデルのカタログにない組み合わせ（モデルが存在しない、またはモデルがその推論強度に対応しない）は不正として起動を中止する。省略した項目は上の値になる。
- `[tasks].max_concurrent` は同時に実行するバックグラウンドタスクの上限（1以上の整数）である。
- `*_ms` のうちタイマーとして使う値（`transcript_retention_ms` 以外）は、Node.jsのタイマー上限である `2147483647` 以下でなければならない。

## 15. 記録の保持とクリーンアップ

エージェントのセッションは `LUNA_HOME/sessions/<YYYY-MM-DD>/<セッションID>.jsonl` に記録する。1行目はセッションの種類・ラベル・モデル、2行目はシステムプロンプトとし、以後はメッセージ（入力、モデルの応答、ツールの結果）・モデルの変更・圧縮の内容を1行ずつ追記する。日付は開いた日のローカル日付とする。Lunaを再起動してもセッションは復元しない。
起動時および `transcript_cleanup_interval_ms` ごとに、最終更新から `transcript_retention_ms`（デフォルト7日）を過ぎた記録と、空になった日付のディレクトリを削除する。削除に失敗した記録は次回のクリーンアップで再試行する。

### 15.1 ワークスペースのゴミ箱

エージェントは、要らなくなったものを `.trash/<捨てた日のローカル日付 YYYY-MM-DD>/` へ、ワークスペースでの相対パスのまま移して捨てる。起動時と6時間ごとに、日付から14日経った日になった日付フォルダを中身ごと削除する。日付の形でない名前はwarnログ `workspace.trash.unknown_entry` を記録して残す。削除するまでの間はダッシュボード（§21）に表示し、必要なら元の場所へ戻せる。

## 16. エラーハンドリングとシャットダウン

| 事象                         | システムの挙動                                                                                                                                   |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 実行の失敗                   | ログを記録し、セッションを閉じて会話セッションを終える。未開始のキューは新しいセッションで処理する。                                             |
| 実行の一時的な失敗           | §8のとおり同じセッションで再実行する。上限を超えたら「実行の失敗」と同じ扱い。会話（記憶保存を含む）・イベント実行・作業エージェントに適用する。 |
| ツールの失敗                 | 失敗の内容をツールの結果としてエージェントへ返し、同じ実行の中で立て直させる。                                                                   |
| 認証の失敗                   | §8.1のとおり、その実行を再試行せずに失敗とし、ダッシュボードに再ログインが必要であることを示す。                                                 |
| セッション記憶保存の失敗     | エラーログを記録してセッションを閉じる。リトライは行わない。                                                                                     |
| 日次整理タスクの失敗         | エラーログを記録してセッションを閉じる。次回cron時刻まで待機。                                                                                   |
| スケジュールのcheck失敗      | エラーログを記録し、エージェントを起動しない。次回の発火時刻まで待機。                                                                           |
| バックグラウンドタスクの失敗 | §20.4のとおり失敗として記録し、依頼元へ `failure` を通知する。                                                                                   |

### シャットダウン

SIGINTまたはSIGTERMを受信すると、新規メッセージとHTTPイベントの受付および定期タスクの開始を停止し、受信済みのキューや実行中の処理がすべて自然完了するのを待機してから安全に終了する。実行中のスケジュールのcheckも完了を待ち、エージェントを起動する結果であればその実行の完了まで待つ。正常終了した会話セッションは、終了前に記憶保存を実行する。バックグラウンドタスクは §20.7 のとおり中断してキューへ戻す。

## 18. HTTPイベントAPI

`POST /events` に `Content-Type: application/json` で以下のオブジェクトを送る。同じサーバーはAssistの会話エージェントの `POST /home-assistant/conversation`（§22.4）も受け付ける。その他のパスやメソッドは提供しない。

```ts
type HttpEventRequest =
	| {
			execution: "one_shot";
			response_mode: "async" | "wait";
			event: { type: string; data: JsonValue };
	  }
	| {
			execution: "conversation";
			response_mode: "async" | "wait";
			session_id: string; // 1〜128文字
			event: { type: string; data: JsonValue };
	  };
```

`one_shot` は新しいセッションで実行して終了時に閉じる。`conversation` は `session_id` ごとの会話セッションへ投入し、Discord会話と同じ集約・steer・アイドル終了を適用する。HTTP会話の初回履歴は空とする。`session_id` は `one_shot` では指定できない。

`async` は受付直後に `202 {"request_id":"..."}` を返し、結果取得用のAPIは設けない。`wait` は実行の終了まで接続を維持し、`http_respond` で指定されたHTTPステータスとJSON本文を返す。指定できるステータスは200〜599で、本文を持てない204、205、304を除く。正常終了まで `http_respond` がなければ `204`、実行に失敗したら `500 {"error":"execution_failed","request_id":"..."}` を返す。会話の複数イベントが同じ実行にまとまる場合も、`request_id` で各リクエストの応答先を指定する。複数の `http_respond` が同じリクエストIDを指定した場合、最初の1件だけを受け付け、後続はツールの失敗とする。`async` のリクエストIDに対する `http_respond` もツールの失敗とする。

JSON形式が不正またはスキーマに合わない入力は `400`、JSON以外のContent-Typeは `415`、受付停止中は `503` を返す。受付処理自体の予期しない例外には `500 {"error":"internal_error"}` を返す。APIは認証、リクエストの再送・重複排除、処理待ちのアプリケーションタイムアウトを提供しない。クライアントが切断しても受理済みイベントの処理は続く。

## 17. ログと監視

ログはすべて標準出力にJSON Lines形式で出力される。
`LOG_LEVEL=debug` または `trace` ではメッセージ本文やプロンプト、ツール引数が出力される。Botトークン等の既知の機密情報はマスクされるが、自由文に含まれる認証情報等の完全な除去は保証されない。
外部監視は、プロセスの死活監視および終了コード（exit code）によって行う。

## 19. リリース

GitHub Actionsの `release` ワークフローをmainブランチから手動実行し、`patch`・`minor`・`major` を指定する。easy-releaseが最新の安定版Gitタグを基準に次のバージョンを計算し、`package.json` の更新後に `pnpm format` を実行し、整形結果を含む準備PRを作成する。安定版タグがない場合の基準は `0.0.0` とする。

準備PRのmainへのマージを契機に、`vX.Y.Z` 形式のタグとドラフトReleaseを作成する。通常のPR、未マージで閉じたPR、別リポジトリからのPRは公開対象にしない。Linuxのamd64・arm64向けDockerイメージをビルドし、GitHub Artifact Attestationsを付与する。成功した後にGHCRの `latest` タグを更新し、GitHub Releaseを公開する。ビルドや証明の付与に失敗した場合はドラフトのまま保持し、`latest` は更新しない。

## 20. バックグラウンドタスク

### 20.1 目的と構成

会話やイベント実行（依頼元）は、数分以上かかる調査・制作・多数のツール呼び出しを伴う作業を `task_create` で作業エージェントへ委任し、完了を待たずに実行を終える。作業エージェントは `LUNA.md` と `MEMORY.md` を事前に読み込まない別のセッションで作業し、Discordへは投稿しない。依頼元への伝達はすべて `task_report` と依頼元への通知イベントを介する。

### 20.2 依頼元が使うツール

| ツール         | 入力                                                                | 結果                               |
| -------------- | ------------------------------------------------------------------- | ---------------------------------- |
| `task_create`  | `{ title: string(1〜120文字), instructions: string(1〜20000文字) }` | `{ task_id, status: "queued" }`    |
| `task_message` | `{ task_id: string, text: string(1〜8000文字) }`                    | `{ task_id, status }`              |
| `task_cancel`  | `{ task_id: string, reason?: string(1〜2000文字) }`                 | `{ task_id, status: "cancelled" }` |

- 文字列は前後の空白を除いた長さで検証する。制約を満たさない入力はツールの失敗となる。
- `task_message` と `task_cancel` は、依頼元から見えるタスク（§20.5）で、かつ終了していないものだけに使える。それ以外はツールの失敗とする。
- 作業エージェントは `task_create` を使えない。

### 20.3 作業エージェントの入力とツール

作業エージェントのツールは、§9の表で「作業エージェント」が◯のものとする。入力は次の種類のメッセージで渡す（§5.5）。

```ts
type TaskAssignment = {
	// kind: "task_assignment"
	id: string;
	title: string;
	instructions: string;
	origin: string; // 依頼元の会話セッションキーまたはイベント種別
	created_at: string;
	attempt: number; // 1から始まる実行回数
	previous_reports: TaskReportJson[];
	messages: TaskMessageJson[]; // これまでの全メッセージ
};
type TaskMessages = { task_id: string; messages: TaskMessageJson[] }; // kind: "task_message"
type TaskCheck = { task_id: string }; // kind: "task_check"

type TaskReportJson = {
	seq: number;
	kind: TaskReportKind;
	summary: string;
	artifacts: string[];
	reported_at: string;
};
type TaskMessageJson = { id: string; text: string; received_at: string };
```

`task_report` の入力は `{ kind, summary: string(1〜4000文字), artifacts?: 絶対パスの配列 }` とし、`kind` は次のとおり。

| `kind`      | 状態への影響    | 依頼元への通知                 |
| ----------- | --------------- | ------------------------------ |
| `progress`  | 変化なし        | しない（タスク一覧にのみ反映） |
| `milestone` | 変化なし        | する                           |
| `question`  | `waiting_input` | する                           |
| `result`    | `completed`     | する                           |
| `failure`   | `failed`        | する                           |

作業エージェントは、作業を終える時に成果物と続きに要るものを残し、試行の環境、途中のコピー、やり直しの残りをゴミ箱（§15.1）へ移す。タスクが成功した後に、繰り返しそうな複数手順のやり方が効いた場合や、skillの誤り・抜けが分かった場合だけ、skillを1つまで直すか作る。読んだskillの修正、既存の広いskillの修正、新しいskillの作成の順に選び、変える前に `SKILL.md` を読む。そのskillのディレクトリだけをワークスペースのGitにコミットし、結果の報告で触れる。

### 20.4 状態遷移と実行

```text
queued ──(実行枠が空く)──► running ──result──► completed
  ▲                          │  └─failure / 実行失敗──► failed
  │                          │question
  │                          ▼
  └──(message受信)──── waiting_input
任意の未終了状態 ──task.cancel──► cancelled
```

- 同時に `running` にできるタスクは `[tasks].max_concurrent`（デフォルト2）件までとし、超えたタスクは作成順に待機する。`waiting_input` は実行枠を使わない。
- `queued` から実行を始めるたびに `attempts` を1増やし、新しいセッションで `task_assignment` を渡す。`attempts` が5を超えた場合は実行せず失敗とする。
- 実行が終わった時点で未配送のメッセージがあれば、同じセッションで `task_message` を渡して続行する（状態は `running` に戻る）。
- 終了報告（`result`・`failure`・`question`）がないまま実行が終わった場合は、一度だけ `task_check` を渡す。再び終了報告がなければ失敗とする。
- 実行の一時的な失敗は §8 のとおり再実行する。それ以外の実行の失敗・中断は、タスクの失敗とする。
- `question` で待機したセッションは同じプロセス内で保持し、メッセージ受信時に同じセッションで `task_message` を渡して再開する。プロセスの再起動で保持が失われた場合は、新しいセッションで `task_assignment` から再開する。
- 実行中のタスクへのメッセージは、割り込み入力として同じ実行へ渡す。
- `task_cancel` は実行を中断し、以後の実行を開始しない。実行済みの外部作用は取り消さない。
- 終了したタスクのセッションは閉じる。

### 20.5 公開範囲とタスク一覧

- Discordのギルドチャンネルまたはギルドスレッドの会話から作成したタスクは、すべての会話から見える。DM・HTTP会話・イベント実行から作成したタスクは非公開とし、作成した会話とイベント実行からだけ見える。イベント実行からはすべてのタスクが見える。
- 会話とイベントの入力の `tasks` には、見えるタスクのうち未終了のもの、および終了から24時間以内のものを、更新が新しい順に最大20件含める。

```ts
type TaskSummary = {
	id: string;
	title: string;
	status: "queued" | "running" | "waiting_input" | "completed" | "failed" | "cancelled";
	origin: string;
	created_at: string;
	updated_at: string;
	latest_report: { kind: TaskReportKind; summary: string; reported_at: string } | null;
	undelivered_messages: number;
};
```

### 20.6 依頼元への通知

通知する報告は `luna.task.reported.v1` イベント（`source: "luna/task"`、`subject` はタスクID、`data` は `{ task: TaskSummary, instructions: string, report: TaskReportJson }`）として依頼元へ届ける。`instructions` は依頼時の指示で、結果を受け取る実行が新しいセッションでも、結果をどう扱うかが分かるようにする。

- 依頼元が会話の場合は、その会話セッションへ通常の受付イベントとして渡す。セッションが終了していれば新しいセッションで受け付ける。
- 依頼元がイベント実行の場合は、新しいワンショット実行として渡す。実行を始めた時点で配送済みとし、その実行が失敗しても再配送しない。シャットダウン時はこの実行の完了を待つ。
- シャットダウン開始後の通知と、受付停止中の会話へ渡せなかった通知は未配送として残し、次回起動時に配送し直す。会話へ受け付けた後にプロセスが終了した場合の再配送は行わない。
- ランタイム起因の失敗（試行回数超過、最終報告なし、実行の失敗など）は、`failure` の報告として記録し通知する。

### 20.7 永続化と再起動

- タスクは `LUNA_HOME/tasks/<task_id>.json` に1件1ファイルで保存し、一時ファイルからの置き換えで更新する。読み込めないファイルやスキーマに合わないファイルはエラーログを記録して読み飛ばす。
- 起動時に `running` だったタスクは `queued` に戻して再開する（`attempts` は再開時に増える）。作業エージェントには、前回の試行が中断されたことを `attempt` と `previous_reports` で伝え、外部作用のやり直し前に確認させる。
- シャットダウン時は実行中のタスクを `queued` に戻し、実行を中断して `wait` を打ち切る。中断した実行の終了、セッションを閉じること、状態の保存を待ってから終了する。`question` で待機中のセッションも閉じる。

## 21. ダッシュボード

Lunaは起動中常に、HTTP APIとは別のポートで閲覧専用のダッシュボードを提供する。`GET /` はHTMLページ、`GET /api/snapshot` は現在の状態のJSONを返し、どちらもキャッシュさせない（`cache-control: no-store`）。ページは3秒ごとにスナップショットを取得して表示を更新する。それ以外のパスは `404`、スナップショット取得中の予期しない例外は `500 {"error":"internal_error"}` を返す。

スナップショットは取得時点のメモリ上の状態であり、永続化しない。

| 項目            | 内容                                                                                                                                                                                                                                                               |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `agent`         | ChatGPTの認証状態（認証済み・再ログインが必要・未ログイン）、最新の使用枠、直近の障害、開いているエージェントのセッション（種類・ラベル・モデル・フェーズ・再試行回数）                                                                                            |
| `conversations` | 開いている会話セッションごとのフェーズとその開始時刻、未処理の入力件数、セッションID、再試行回数、モデル設定、待機中ならアイドル期限                                                                                                                               |
| `events`        | 実行中のワンショット実行（ハートビート・スケジュール・日次整理・タスク報告・HTTP）のイベント、フェーズ、開始時刻                                                                                                                                                   |
| `tasks`         | 実行枠の上限と使用数、未完了のタスクと終了から24時間以内のタスク（最新50件）の全内容                                                                                                                                                                               |
| `automation`    | ハートビートの次回発火時刻、日次整理のcronと次回発火時刻、登録済みスケジュールジョブの定義と次回発火時刻                                                                                                                                                           |
| `workspace`     | ワークスペースのあるファイルシステムの全容量と空き容量、ゴミ箱の日付フォルダごとの削除日と中身（直下の名前）                                                                                                                                                       |
| `homeAssistant` | HAの接続を設定していなければ `null`。設定していれば、WebSocketの接続状態（接続中・接続済み・再接続待ち）とその開始時刻、再接続の予定時刻、直近のエラー、`home-assistant.toml` の状態（なし・有効・不正）と内容または検証エラー、状態変化で起動した回数と最後の時刻 |
| `activity`      | 直近の出来事（info以上のログ）最大500件。`LOG_LEVEL` に関係なく本文（payload）を含み、詳細と本文はそれぞれ4000文字で切り詰める                                                                                                                                     |

ハートビートの次回発火時刻は、実行中（完了後に次の間隔を抽選する前）は持たない。

## 22. Home Assistant 連携

環境変数 `HOME_ASSISTANT_URL` と `HOME_ASSISTANT_TOKEN`（§14.2）を両方指定すると、Home Assistant（以下HA）の状態の取得と操作、状態変化をきっかけにした実行が有効になる。片方だけの指定は起動を中止する。どちらも指定しなければ、この節の22.1〜22.3は無効となる。Assistの会話エージェント（22.4）はHAへの接続を使わないため、指定の有無にかかわらず受け付ける。

HAのトークンを持つユーザーの権限で、すべてのドメイン・サービス・エンティティを操作できる。呼べるサービスや対象の制限、実行前の確認は設けない（§3）。トークンは `DISCORD_BOT_TOKEN` と違い、シェルツールとcheckの子プロセスにも渡す。

### 22.1 ツール

会話・イベント実行・作業エージェントのすべてに渡す。HAへのリクエストはREST API（`/api/...`）に `Authorization: Bearer <トークン>` を付けて送り、15秒でタイムアウトする。HAが2xx以外を返した場合と、タイムアウト・接続の失敗は、HAの応答本文（あれば）を含めたツールの失敗とする。

| ツール             | 入力                                                                                            | 結果                                                                                                                   |
| ------------------ | ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `ha_list_entities` | `{ domain?, area?, name?, entity_ids?: string[], max?: 1以上の整数 }`                           | `{ entities: [{ entity_id, state, friendly_name, area?, device? }], total, truncated }`                                |
| `ha_get_state`     | `{ entity_id }`                                                                                 | HAの状態オブジェクト（`entity_id`、`state`、`attributes`、`last_changed`、`last_updated`）。存在しなければツールの失敗 |
| `ha_list_services` | `{ domain? }`                                                                                   | `[{ domain, services: { <サービス名>: { description?, fields: { <フィールド名>: 説明 } } } }]`                         |
| `ha_call_service`  | `{ domain, service, entity_id?: string \| string[], data?: object, return_response?: boolean }` | `{ changed_states: [{ entity_id, state }], service_response? }`                                                        |

- `domain` と `service` は `^[a-z0-9_]+$`、`entity_id` は `^[a-z0-9_]+\.[a-z0-9_]+$` に合わなければ検証エラーとする。
- `ha_list_entities` は `entity_ids`（指定時は他の条件より優先）、`domain`（完全一致）、`area`、`name`（`entity_id` か `friendly_name` に大文字小文字を区別せず含む）の順に絞り込み、`max`（省略時200）件までを返す。`total` は絞り込み後の件数、`truncated` は `max` で切ったかどうか。各要素は属性を含めない。
- `area` を指定した場合だけ、WebSocket API（22.2）でエリア・デバイス・エンティティの登録情報を取得し、エンティティのエリア（エンティティ自身のエリア、なければデバイスのエリア）の名前かIDが一致するものを残す。このとき各要素に `area` と `device`（デバイス名）を付ける。登録情報は5分間キャッシュし、WebSocketが接続していなければツールの失敗とする。
- `ha_call_service` は `data` に `entity_id` を加えた本文を `POST /api/services/<domain>/<service>` に送る。`return_response` が真ならクエリ `?return_response` を付け、HAが返す `service_response` を結果に含める。

### 22.2 WebSocket接続

起動時に `HOME_ASSISTANT_URL` から導いた `ws(s)://.../api/websocket` へ接続し、`auth_required` に対してトークンで認証してから、`state_changed` イベントを購読する。

- 30秒ごとに `ping` を送り、10秒以内に `pong` がなければ切断して再接続する。
- 切断・認証の失敗・接続の失敗では、5秒・10秒・30秒・60秒（以後60秒）待って再接続する。認証が成功したら待ち時間を最初に戻す。切断中に起きた状態変化は補完しない。
- 接続・切断・認証の失敗はログ（`home_assistant.ws.*`）に記録し、状態をダッシュボード（§21）に示す。

### 22.3 状態変化をきっかけにした実行

ワークスペースの `home-assistant.toml` に、どのエンティティの状態変化でルナを起動するかを書く。エージェントが自分で編集する。ファイルがなければ何も起動しない。

```toml
watch = ["binary_sensor.front_door", "climate.*"]
ignore = ["sensor.*_battery"]
cooldown_seconds = 30   # 省略時30
```

- `watch` と `ignore` は `entity_id` のパターンの配列（省略時は空）。`*` は任意の文字列（`.` を含む）に一致し、それ以外の文字は完全一致とする。`cooldown_seconds` は0以上の数。
- 状態変化を受けるたびにファイルの更新時刻を確かめ、変わっていれば読み直す（再起動は不要）。不正なファイルはその更新時刻につき1回だけエラーログ `home_assistant.watch_config_invalid` を記録し、何も起動しないものとして扱う。
- 次をすべて満たす状態変化を起動の対象とする: 変化前と変化後の状態がどちらもある、`state` の値が変わった（属性だけの変化は対象外）、`watch` のいずれかに一致し `ignore` のどれにも一致しない、同じエンティティの前回の起動から `cooldown_seconds` 以上経った。前回の起動時刻はメモリ上に持ち、再起動で消える。
- 対象の状態変化は `home_assistant.state_changed.v1` イベント（`source: "home_assistant"`、`subject` はエンティティID、`occurredAt` は変化後の `last_changed`、`data` は `{ entity_id, friendly_name, old_state, new_state, unit, device_class }`。値がない項目は `null`）として、キー `home_assistant:state_changes` の会話セッションへ渡す。入力の種類は `home_assistant_state`（§5.5）。集約・steer・アイドル終了・セッション記憶保存はDiscordの会話と同じとし、初回履歴は空とする。

### 22.4 Assistの会話エージェント

HAのカスタム統合 [ha-luna](https://github.com/shun-shobon/ha-luna) を入れると、HAのAssist（音声・テキスト）で会話エージェントとしてLunaを選べる。統合はHTTP API（§18と同じサーバー）の `POST /home-assistant/conversation` を呼ぶ。HAとLunaが別のホストにある場合は `LUNA_HTTP_HOST=0.0.0.0` が必要で、認証は行わない（§3）。

```ts
type AssistRequest = {
	text: string; // 1文字以上
	language: string;
	conversation_id: string; // 1〜128文字
	device_id: string | null;
	satellite_id: string | null;
	device_name: string | null;
	area_name: string | null;
	user_name: string | null;
};
type AssistResponse = { speech: string | null; continue_conversation: boolean };
```

- 受け付けた発話は `home_assistant.assist.requested.v1` イベント（`source: "home_assistant"`、`id` はリクエストID、`data` はリクエスト本文）として会話セッションへ渡す。入力の種類は `assist_request`。
- 会話セッションは `device_id` があれば端末ごと（キー `home_assistant:assist:device:<device_id>`）、なければHAの会話IDごと（キー `home_assistant:assist:conversation:<conversation_id>`）とする。集約の待機（`debounce_ms`）は行わず、受け付けたらすぐに実行する。それ以外（steer・アイドル終了・セッション記憶保存）はDiscordの会話と同じとし、初回履歴は空とする。
- エージェントは `assist_respond`（入力 `{ request_id: string, speech: string(1〜2000文字), continue_conversation?: boolean }`、省略時 `false`）で読み上げる文を返す。呼ばれた時点でHTTPの応答を返し、実行は続く。同じリクエストIDへの2回目以降、応答待ちでないリクエストIDへの呼び出しはツールの失敗とする。`assist_respond` は会話とイベント実行に渡す。
- `assist_respond` がないまま実行が正常に終わったら `200 {"speech":null,"continue_conversation":false}`、実行が失敗したら `500 {"error":"execution_failed"}` を返す。
- JSON形式が不正またはスキーマに合わない入力は `400 {"error":"invalid_request"}`、JSON以外のContent-Typeは `415`、受付停止中は `503 {"error":"unavailable"}` を返す。シャットダウン時に応答待ちのリクエストには `500 {"error":"execution_failed"}` を返す。

## 23. デスクトップ

ルナ専用のデスクトップを任意で入れられる。人は neko（WebRTCの画面共有）で同じ画面を見て、マウスとキーボードで操作に加われる。Lunaのプロセスとは独立した systemd のサービス群で、Linux（Ubuntu 24.04）のホストに `deploy/desktop/install.sh` を root で実行して入れる。Lunaはデスクトップの有無に依存せず、ルナはワークスペースのskillを通じてだけ使う。

| サービス                  | 内容                                                                                                                                                                             |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `luna-desktop-xvfb`       | 画面 `:99`（1440×900）。解像度は固定                                                                                                                                             |
| `luna-desktop-openbox`    | ウィンドウマネージャー                                                                                                                                                           |
| `luna-desktop-dbus`       | デスクトップのD-Busセッション。AT-SPI（アクセシビリティ）のバスもここから起動する                                                                                                |
| `luna-desktop-pulseaudio` | 音声の出力先（null sink）                                                                                                                                                        |
| `luna-desktop-chrome`     | Google Chrome。プロファイルは `LUNA_HOME/desktop/chrome-profile` でログイン状態を保つ。CDPを `127.0.0.1:9222` で待ち受け、アクセシビリティツリーを公開する。終了すると再起動する |
| `luna-desktop-neko`       | neko。`8080/tcp` で閲覧画面とAPI、`59000/udp` でWebRTCを待ち受ける                                                                                                               |
| `luna-desktop.target`     | 上記をまとめて起動・停止する                                                                                                                                                     |

すべて実行ユーザー `luna` で動く。共通の環境変数（`DISPLAY`、`XDG_RUNTIME_DIR=/run/luna-desktop`、D-BusとPulseAudioのソケット、`LANG=ja_JP.UTF-8`）は `/opt/luna-desktop/etc/session.env` に置く。

neko の設定は `/opt/luna-desktop/etc/neko.yaml` と、ホストごとの値を持つ `/etc/luna-desktop/neko.env`（root のみ読める）に分ける。`neko.env` には WebRTC で広告するホストのLANのIP（`NEKO_WEBRTC_NAT1TO1`）、閲覧・操作用と管理者用のパスワードを書く。`install.sh` は `neko.env` がなければ、ホストの最初のIPと乱数のパスワードで作る。

- 認証: neko の multiuser。どちらかのパスワードと任意の表示名でログインする
- 操作権: 操作した人がそのまま操作権を得る（`implicit_hosting`）。ルナの操作（CDP・AT-SPI・xdotool）は neko の操作権を経由せず、人の操作と排他にしない
- 配信: 誰かが見ている間だけ映像をエンコードする。ポインタを映像に描き込み、ルナが動かしたポインタも見える

`install.sh` は skill `luna-desktop`（`SKILL.md`、操作用の `scripts/desktop.py`、CDP用の `playwright-core`）を `LUNA_HOME/workspace/.agents/skills/luna-desktop/` に上書きで置く。

- `desktop.py` は AT-SPI でアプリの部品を番号付きで一覧し、番号を指定して操作する。部品が操作に応じない時はポインタやキーの入力に切り替える。ASCII以外の文字はクリップボードからの貼り付けで入力する
- 各操作のあとに画面全体のスクリーンショットを `/run/luna-desktop/screens/`（直近30枚）に保存し、直前の画面から変わったかを返す
- 入力欄の値を置き換えた時は、値を読み直して一致したかを返す
- `wallpaper` は指定した画像を `LUNA_HOME/desktop/wallpaper` へコピーして、すぐに貼り替える
